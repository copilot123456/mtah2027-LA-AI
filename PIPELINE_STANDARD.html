What it is, and why we built it

Each of us is working on our own branch, trying the idea that might break our score open in a good way. The risk of that setup is obvious: everyone edits the same decoder, the same fill, the same config — and Wednesday's merge becomes a conflict resolution session.

The framework removes that risk. The pipeline is now a list of named stages declared in one file. Your experiment replaces one entry in that list with your handler. The audited core (src/ stage functions, config.py, the submission path) stays untouched, your diff is one line, and comparing approaches becomes mechanical — which is exactly what we need for Wednesday and for using P6 as the yardstick between our approaches.

Think LEGO, not spaghetti: each stage is a brick with a fixed shape (inputs it needs, outputs it produces). The declaration file is the instruction sheet — swapping a brick never restructures the model.

The one file you edit: pipeline_spec.py

Every stage of the pipeline, in order, with what each one needs and produces:

# pipeline_spec.py — the whole pipeline, top to bottom
SPEC = [
    Step("load",      S.load,        provides=("arrays",)),
    Step("ball_fill", S.ball_track,  requires=("arrays",), provides=("track",)),
    Step("emission",  S.emission,    requires=("arrays", "track"), provides=("emission",)),
    Step("decode",    S.decode_step, requires=("arrays", "track", "emission"), provides=("decoded",)),
    Step("x_policy",  S.x_policy,    requires=("arrays", "emission", "decoded"), provides=("labels",)),
    Step("summary",   S.summarize,   requires=("arrays", "track", "decoded", "labels"), provides=("summary",)),
]

Swapping a stage — your ViT example, literally

Gap filling with ViT instead of the current handler is one binding:

# your branch — pipeline_spec.py
from src.vit_fill import ball_track        # your fn(ctx, cfg) -> None, with a docstring

SPEC = [
    Step("load",      S.load,       provides=("arrays",)),
    Step("ball_fill", ball_track,   requires=("arrays",), provides=("track",)),  # ← was S.ball_track
    # … everything else unchanged …
]

Adding a stage works the same way: write any fn(ctx, cfg) -> None with a docstring, then append a Step(...) line. Reordering is moving lines. That's the whole API.

Three moving parts

1. Step — a stage's name, its function, and the data it requires/provides.

2. Ctx — the tray that carries data (arrays, track, emission, decoded, labels, summary, plus a free-form extra bag) from one stage to the next.

3. The runner — validates the whole list before running anything, then executes it in order and returns the labels + summary that python -m src.submit writes out.

Guard rails built in

⚠ Fail fast, before a run: a stage that needs data nobody produced is reported by name immediately — not as a cryptic error 20 seconds in.

📝 Comments are enforced: a handler without a docstring is rejected. Every brick must say what it is.

🔒 The default never drifts: the shipped declaration must keep reproducing LA+AI.csv byte-for-byte — a test fails the build if it doesn't.

Rules that do not change

The framework makes experiments easy. It does not make adoption easy — that stays evidence-gated, same as before.

Frozen default

The default pipeline_spec.py must always regenerate LA+AI.csv byte-identically (md5 0ed725f70f4a230cd50ee9023dda60b6).

Evidence rule

Config / decoder / emission changes need >0.02 paired on IDSSE, pre-declared in dossier §7 — never adopted on taste. No tuning on eval, GT, the video or the public window. Ever.

Never touch

evaluation/, starter/, games.py. Never commit data/*, weaken .gitignore, or rewrite history.

Every commit

Tests green, and if a kept change alters output, the CSV is regenerated in the same commit.

⚠ REQUIRED: share every framework change with the team

This standard only works if everyone is running the same standard. Any change to the common framework — a new step type, a contract change, a validation rule, a doc update — must be shared with the rest of the team before it merges. Silent changes break adoption; a framework nobody knows about is a framework nobody uses.

  1. Build on your branch. Don't edit the contract on main directly.
  2. Verify. Tests green + default output byte-identical (if behaviour changed, the external-evidence rule applies instead — see Rules).
  3. Share the proposal with the team. Post what changed, why, and your verification results — in the team chat and/or at the Wednesday 11-11 sync. Include the diff.
  4. Team agrees → merge. Only then does it enter the final branch. The Wednesday meeting is the adoption checkpoint.
Rule of thumb: swapping a handler inside your own branch needs no permission — that's what the framework is for. Changing the framework itself (the contract, the runner, the validation, the defaults) always goes through the four steps above.
